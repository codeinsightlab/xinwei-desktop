# 窝囊费产品需求文档交叉审查

审查日期：2026年11月3日。

审查对象：用户粘贴的《窝囊费》产品需求文档 PRD V1.0；对照本项目《薪慰桌面工资进度工具产品需求文档》。本次只输出审查结论，不修改两份需求基线。

采用主审、产品与体验独立审查、计算与架构独立审查三个视角。独立审查后，主审提出质询，复核严重度、触发条件及是否把方案偏好误当成缺陷。

## 结论

文档的产品定位、计薪主公式及跨平台分层方向成立，可以启动计算和窗口原型验证。若作为完整首版开发及发布验收依据，还需要收口以下规则。

这里的“高”表示实现对应功能前需解决，“中”表示需补齐规格，不等同于原文的功能P0、P1。

## 共同确认的问题

### 1 高 隐藏金额的承诺没有形成完整功能

定位：场景F；FR-009系统托盘；FR-012隐私保护；9.3 ApplicationSettings。

场景F要求通过托盘隐藏金额，FR-012只规定快速隐藏窗口，而托盘仍能查看工资摘要。隐藏小窗后打开托盘，工资仍可能出现在共享屏幕中。配置模型也没有共享隐私状态。

修订：增加全局金额隐藏状态，并覆盖小窗金额、月度金额、速率、托盘摘要、设置预览和可访问性文本。状态跨窗口同步并记住选择。用户主动编辑工资时，明确输入值的显示行为。隐藏窗口与隐藏金额作为两个不同操作定义。

### 2 高 整月重算缺少变化预览

定位：FR-002计算原则；5.3修改工资；6.2补班、6.3请假、6.4加班。

重分摊模型本身正确，但调整未来日期会改变过去已经显示的金额。例：2026年11月按21个工作日、每天8小时、月薪16800元，11月3日10:30本月已赚950元。增加一个未来补班日后，分母变为176小时，本月金额降为906.82元。

这不是数据丢失，但没有预览就容易被理解为程序算错。

修订：工资、排班、特殊日期作为草稿统一保存；保存前展示今日金额、本月金额和本月总工时的前后变化；按钮写明“保存并重算本月”。说明补班和加班时段只是重分配固定月薪，不产生额外收入。

### 3 高 跟随设备时区和夏令时验收没有明确规则

定位：FR-003；6.9跨时区；9.2 WorkSchedule.timezone；10.2计算精度验收。

文档选择设备当前时区，又要求夏令时自动测试，但未定义按真实经过秒数还是墙钟工时计算，也未规定不存在或重复本地时刻如何解释。例如夏令时切换日的01:00至04:00，不能仅靠文字标签判定实际经过时长。

持久化timezone字段与设备跟随策略并不必然冲突，但需要明确何时更新，以及变更时是否重建整月工作区间。

修订二选一：首版固定北京时间并暂缓全球时区验收；或保留设备时区策略，明确时区变更、夏令时消歧、区间边界及真实秒数口径，并给出确定输入和输出的测试。

### 4 中 首版功能优先级互相覆盖

定位：FR-004桌面组件；FR-007桌面外观；第11节路线图。

透明度在FR-004中属于P0内容，在FR-007又属于P1；FR-007标为P1，却说首版实际需要经典和极简两种模式。开发无法从文档明确判断哪些内容可以延期。

修订：用一张版本范围表作为唯一依据。建议首版保留单一布局、置顶、拖动、托盘和隐私开关；多模式、透明度和动画增强移至后续。

### 5 中 金额精度与输入范围尚不构成明确契约

定位：FR-001；4.2.2；9.1 SalaryConfig；9.4 SalarySnapshot。

“小数显示可配置”没有范围，而快照只保留整数分。若允许超过两位小数，亚分精度会在快照生成时丢失；若仅允许0至2位，则需要直接写明。月薪仅限制大于零，没有上限、有限值校验和小数位校验，无法设计统一的大额及非法输入验收。

修订：首版固定显示两位小数，月薪规定最多两位小数、明确上限并拒绝非有限值；精确金额计算与显示取整分离。整数分乘总秒数的中间结果也要校验范围，必要时用精确整数或分数表示。

四舍五入不是错误，无需强制改成向下取整。补充规定本月总额从未取整的总时长独立计算，不累计每日展示金额。例：1元月薪分摊21天，每日显示0.05元，相加为1.05元，但月度值应为1元。该差异需要说明。

### 6 中 非工作时的速率文案可能误导

定位：FR-004组件示例；FR-006工作状态。

若午休时仍显示“+ ¥0.0341/秒”，用户会理解为金额正在增长，而文档规定此时暂停。

修订：区分理论秒薪与当前增长速率。工作时显示增长速率，休息时显示“暂停计薪”；理论速率可放辅助信息中，并明确命名。

### 7 中 性能与兼容性目标缺少测量口径

定位：第7节非功能性需求；10.3 Windows端验收。

100MB内存、1% CPU、72小时稳定性已经注明是目标，但未定义是否包含WebView子进程、测试硬件、窗口状态以及持续增长的判定方式。Windows 10/11也缺少目标版本和处理器架构。

修订：明确首发系统矩阵和基准机；统计应用及所属WebView子进程；规定冷启动前置条件、CPU采样窗口、内存基线与趋势。不要把架构预留macOS写成已验证兼容。

## 对照上一版后应吸收的优点

| 议题 | 交叉审查结论 |
| --- | --- |
| 产品主体 | 用户这版“小窗＋设置”更贴合玩具；上一版独立主面板可以删除，月度信息折叠到小窗或设置 |
| 首次启动 | 配置完成直接进入桌面更直接，不必再要求点击“放到桌面” |
| 多工作时段 | 该模型表达午休和其他间隔更统一；需要限制首版编辑复杂度，或先只开放默认两段 |
| 历史计划 | 无历史功能时，不强制引入历史月快照；明确配置变更和系统时间跨月回拨的适用范围即可 |
| 前端框架 | Vue与React均可，不是审查缺陷；启动工程时选定一个并统一 |
| 金额取整 | 四舍五入和向下取整都是可行规则；统一精度、汇总和验收比选哪一种更重要 |
| 名称 | 窝囊费与薪慰属于品牌方向选择，不作为技术问题裁决 |

## 建议冻结的最小首版

只做小窗和设置；固定月薪；默认每周作息和两段工作时间；日期工作或休息覆盖；今日为主、本月为辅；托盘、置顶、拖动、全局隐藏金额；本地保存与恢复；Windows安装和退出。

先冻结时区与精度契约，再实现计算核心；同时验证无框窗口和托盘。多模式、透明度、复杂排班和历史查询暂缓。计薪核心保持平台无关，macOS作为后续实机适配阶段。

这份审查没有执行应用测试。目前只有需求文档，金额示例做了独立算术核对；Windows和macOS运行能力仍需在实现后验证。
